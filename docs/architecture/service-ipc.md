# Fulbr Service and IPC Design

**Status:** implemented, IPC smoke-tested, TUN not yet tested on Windows
**Date:** 2026-11-09
**Scope:** `Fulbr.Service` (privileged), named-pipe protocol, TUN engine supervision.

---

## 1. Why a service

TUN creation, route changes, DNS changes, and (future) persistent WFP filters require
administrator rights. Fulbr keeps the UI unelevated and places these operations in a
narrow Windows service. The service does **not** expose arbitrary commands, file paths, or
raw engine configs.

```
Fulbr.exe (user) ── named pipe ──> Fulbr.Service (LocalSystem)
                                      └── engine-service\sing-box.exe (TUN)
                                            └── engine-service\wintun.dll
```

The service uses a **separate engine directory** (`engine-service`) so its orphan cleanup
cannot kill a proxy-mode engine started by the UI.

---

## 2. Pipe protocol

- Pipe name: `Fulbr.Service`
- Transport: named pipe, byte mode, one request per connection, newline-delimited JSON.
- Max request line: 32 KiB.
- ACL: LocalSystem and Administrators full control; Builtin Users read/write.
- Caller identification: `RunAsClient` impersonation is attempted; if unavailable, the
  service logs `local-user (ACL-validated)`. The ACL is the current boundary. A random
  per-boot pipe name or per-user token is a pending hardening item.
- Commands:
  - `{"command":"ping"}`
  - `{"command":"status"}`
  - `{"command":"start","link":"<share link>","interfaceName":"Fulbr"}`
  - `{"command":"stop"}`
  - `{"command":"recover"}`
- `start` validates the share link with the same strict parser used by the UI, rejects
  insecure TLS, builds a TUN config, runs `sing-box check`, starts the engine, waits for
  the diagnostic port and the TUN interface, and only then returns `Connected`.
- No command accepts a filesystem path or an arbitrary engine config.

---

## 3. TUN configuration (generated by the service)

- TUN interface: `Fulbr` (configurable, validated name).
- IPv4: `10.255.255.1/30`; IPv6: `fdfe:dcba:9876:1::1/126`. These avoid the common
  `172.19.0.0/30` range used by Happ/xray TUN adapters on the test machine.
- `auto_route: true`, `strict_route: true`, `stack: gvisor`, MTU 1500.
- DNS: DoH (`https://dns.google/dns-query`) via the proxy outbound, `hijack-dns`.
- Private IPs (`ip_is_private`) are routed direct for LAN access.
- A loopback mixed inbound with random per-session credentials is included for
  diagnostics and optional app-level use.
- Clash API binds `127.0.0.1` with a random secret.

`strict_route` is documented by sing-box to block DNS traffic outside the TUN on Windows
and to prevent Windows multihomed DNS leaks. It may break some applications (the docs cite
VirtualBox); this must be tested in the VM.

---

## 4. Kill-switch status (important)

**No persistent service-owned WFP kill switch is implemented yet.** The current
protection is sing-box's `strict_route`, which is scoped to the engine process. If the
engine crashes, its WFP filters can disappear until the service restarts it. Therefore:

- Do **not** claim fail-closed protection across an engine crash.
- The UI must show the tunnel as degraded/error on engine exit.
- A service-owned WFP filter set (with a watchdog) is the next security milestone.

This gap is intentional and documented rather than hidden.

## 5. Install / test (VM only)

Build:

```powershell
powershell -File tools\build-service.ps1
```

In a Windows 10/11 VM, as Administrator:

```powershell
powershell -File tools\install-service.ps1
powershell -File tools\test-service-pipe.ps1 -Command status
powershell -File tools\test-service-pipe.ps1 -Command start -Link "<test share link>"
```

Stop / remove:

```powershell
powershell -File tools\test-service-pipe.ps1 -Command stop
powershell -File tools\uninstall-service.ps1
```

**Never run the installer on the host without a separate approval.** The service runs as
LocalSystem, creates a TUN adapter, changes routes/DNS, and loads Wintun.

---

## 6. VM verification checklist

- Service starts and survives a reboot.
- Pipe `ping`/`status` work from a normal user account.
- Invalid links are rejected; insecure TLS is rejected.
- TUN adapter `Fulbr` appears; routes point to it while connected.
- DNS queries follow the tunnel; no obvious ISP DNS leak (test).
- Disconnect removes the adapter and restores the previous routes/DNS.
- Force-killing the engine leaves the service alive; status becomes Error/Disconnected.
- Force-killing the service and restarting cleans stale engine/config files.
- Uninstall removes the service, engine, and adapter; user data remains.
- `strict_route` coexistence with VirtualBox/Hyper-V and the VM's antivirus.

Results must be recorded in `IMPLEMENTATION_STATUS.md` and the security test docs. Until
then, TUN mode is **unverified**.
